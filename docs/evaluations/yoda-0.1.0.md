# Yoda audit — all nine skills

Audit date: 2026-10-08. All nine skills were inspected and exercised against a baseline; the strategy correction received a fresh paired follow-up.

## Method

The audit follows hartye-skills' Yoda 0.4.0: inspect the library, then compare behavior with and without instructions. All nine skill names match their directories; descriptions are 139–209 characters and bodies remain under 500 lines. Skill-creator validation, direct-resource checks, positional-argument scans and a targeted invisible-codepoint scan passed for all nine. These are structural checks, not a safety certification.

Two fresh agents received identical frozen facts, CLI documentation and isolated ledgers. One read the designated skills and required resources; the baseline could use CLI/schema documentation but no skill bodies or craft. Each completed two tasks per skill: **18 pairs / 36 runs**. Before body access, both chose the expected primary skill on **18/18** positive and near-miss metadata prompts. This measures prompted metadata routing, not host automatic activation.

Five criteria per case were fixed before execution. A fresh independent reviewer received copies with arm labels concealed and inspected the reports, linked drafts, command receipts and ledger state. Pass/partial/fail/unknown coverage is descriptive; it is not an effectiveness estimate. Root and reviewer independently validated all 36 ledgers. Existing records were retained, with only requested project/plan updates; prior observations, reactions and experiments were preserved.

The products and policy packets were synthetic. Research cases used a fixed primary-source packet rather than live searches. Each arm shared one context across its 18 tasks, so later cases could benefit from earlier tasks. Labels were hidden, but content may reveal guidance. The sample is small and selected; no general skill advantage, marketing effectiveness, host triggering or safety follows.

## Findings and corrections

The README initially overstated individual skill-folder portability. Loading requires the shared repository layout, including craft, CLI documentation and setup scripts; the README now states this. The strategy description now explicitly includes games/projects. Both initial metadata runs had already routed the game prompt correctly, so this is a coverage clarification rather than a measured routing fix.

The initial assisted strategy plan assigned `discord` to an unnamed maker community. Its packet established generic community rules, not that platform. The original output and grade are retained. The strategy body now forbids inferring a platform or permission from generic rules and requires the narrative, source and recorded channel to agree. A fresh matched rerun of both strategy tasks checks that correction; it does not replace the initial scores.

The four follow-up ledgers freshly validate and every original record is unchanged. Both arms pass the separately marked platform/source/narrative gate: the unspecified showcase stays conditional outside the ledger, while saved initiatives use GitHub or direct diagnosis. The revised-skill outputs satisfy all ten original criteria; the baseline satisfies nine fully and one partly, because its Orbit plan does not specify a review date if five attempts are unavailable. No material platform blocker remains in these cases.

These follow-ups bring the total to **40 task runs**, without changing the original 18-pair scores. Both arm agents were fresh. The independent reviewer had seen the initial evaluation, with new concealed labels for the follow-up; content could still reveal guidance. The added consistency gate is a targeted regression check, not a retroactively prespecified initial criterion.

Baseline completeness omissions and their evidence remain in the criterion assessment. They are not rewritten as failures of the installed skill.
